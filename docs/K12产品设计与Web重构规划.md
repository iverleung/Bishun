# 笔顺工具：K12 长期产品设计与功能探索

日期：2026-11-07。状态：长期产品探索稿。当前优先完成 Web 稳定化和必要功能，之后再评估 App。

Web 的 UI、资源、语音、播放重构和验收已迁至独立的 [Web 重构计划](Web重构计划.md)，以该文档为当前 Web 工作范围。保留本文件路径以兼容既有引用。

## 1. 产品主张与设计前提

建议定位为：**面向 K12 的汉字书写查询与练习助手，让学生快速查到、看懂、自己写出来。**

保留覆盖 K12 的产品范围，首阶段优先验证小学 1—3 年级家庭作业场景；幼儿园以亲子启蒙为主，高年级以快速查证和纠错为主。各学段的需求强度仍是假设，需要访谈验证，不应把同一套低龄界面铺给所有学生。

当前顺序调整为：先重设计 Web UI 与交互，稳定查询、资源、语音和播放，增加必要功能；通过 Web 验收后，逐项决定哪些能力平移到 App，再结合手机的相机、麦克风、分享入口和手写输入增加能力。屏幕练习、教材、课堂、游戏与 AI 保留为长期选项，不自动进入 Web 首轮范围。

本稿默认先服务中国大陆简体规范汉字；繁体、港澳台规范、海外中文可作为独立内容版本。App 的目标平台尚未确定，因此同时比较 Web/PWA、移动 App 和平板，不预先锁定技术栈。

## 2. 当前项目能力盘点

以下以工作区代码为准，包含现有未提交改动；没有覆盖或修改这些改动。

| 能力 | 当前状态 | 产品含义 |
|---|---|---|
| 工程基础 | Vite + ES Modules；HanziWriter、cnchar、cnchar-order 为 npm 依赖 | 已具备继续演进的 Web 基础 |
| 输入查询 | 输入并过滤汉字，最多 20 字；点击播放或回车启动 | 能承接词语、短句和作业字串 |
| 多字展示 | 多张字卡，田字格叠加对角线；点击字格播放单字 | 有批量示范能力，缺少单字详情层级 |
| 顺序播放 | 按字连续播放，显示字序进度，自动滚动到活动字卡 | 可以作为词语学习和课堂示范基础 |
| 播放控制 | 播放、暂停、继续；五档速度 | “继续”主要恢复到字级，会重新从该字首笔开始 |
| 语音 | Web Speech API 朗读笔画名称；可开关 | 已有听觉辅助；不是汉字读音和词义朗读 |
| 设置记忆 | 本地保存速度、语音开关 | 尚无查询历史、生字本和学习记录 |
| 笔画名称 | 页面调用 v3，按字和笔画序号查 cnchar 字典 | 运行主路径不是 README 描述的几何识别算法 |
| 其他识别算法 | 保留 v1/v2 几何识别代码 | 可供研究与回归，不应误认为在线手写识别 |
| 数据加载 | 本站资源优先，失败后顺序尝试多个 CDN；失败字可重试 | 有降级思路，尚不等于完整离线支持 |
| 本站字形数据 | public/hanzi-writer-data 下 48 个 JSON | 是小规模资源集，无法代表完整 K12 字库覆盖 |
| 测试 | npm test 指向 v2；test/run.js 也支持 v3 | 默认测试与页面引擎不一致 |
| 手写练习、拍照查字 | 未接入 | 需要新增输入、交互和验证能力 |
| 拼音、部首、释义 | 页面未提供 | 不能因依赖库可能支持就算作现有产品能力 |
| 教材、账号、多端同步 | 未提供 | 属于新产品模块 |
| 原生 App、安装与离线包 | 未提供相应完整能力 | 需要平台与资源管理设计 |

代码入口：`index.html`、`src/main.js`、`src/style.css`、`src/engine/speech.js`、`src/engine/recognition/v3.js`、`test/run.js`。

### 必须先澄清的质量问题

1. README 的“100% 准确”不能外推为全部汉字准确，更不能作为 K12 教学质量承诺；有限测试集通过与规范逐字审核是不同证据。
2. v3 对缺失字符、缺失笔画名称默认返回“点”；含多个候选的名称直接取最后一个。这可能把未知数据变成确定的教学内容。
3. 动画路径来自 HanziWriter 数据，名称来自 cnchar；要核验两者的笔画数量、顺序、对应关系，不能直接按索引拼接后视作正确。
4. `STROKE_REFERENCE.md` 的分类与例字尚需按来源复核，不能把文档的“严格依据”文字当作完成审核的证明。
5. AGENTS.md 已根据当前代码更新，区分现有实现、已知问题和后续规划；README 中的历史算法和准确率表述仍需后续按验证结果同步。

## 3. 用户与场景

| 人群 | 典型问题 | 首要体验 | 可选扩展 |
|---|---|---|---|
| K／幼儿园及亲子 | 不会输入汉字，注意力短，手指操作粗 | 家长选字、大字示范、少按钮、短时互动 | 基本笔画、名字卡、亲子找字 |
| 小学 1—2 年级 | 这一笔先写什么、下一笔在哪 | 单步示范、笔画名、描写到独立书写 | 课内字单、纸质字帖、家长陪练 |
| 小学 3—6 年级 | 会认不会写、复杂部件、形近字混淆 | 快速查字、关键笔顺、错处复练 | 部件变形、易错字组、听写 |
| 初中 | 作业中临时查证，低频字和字形混淆 | 简洁模式、快速结果、来源说明 | 形近字对照、个人错字集 |
| 高中 | 低频查证、书写规范与效率 | 工具化界面、复杂字拆解、准确来源 | 规范楷书与行楷内容，但需另备教学资源 |
| 家长 | 自己也不确定笔顺，辅导耗时 | 一键演示、作业字单、可打印 | 多孩子本地档案、简短复习建议 |
| 教师 | 临时讲解、投屏、准备练习材料 | 大屏示范、逐笔控制、整组字单 | 课堂练习、分享链接、班级任务 |

年龄、年级都只用于提供默认设置，不直接决定能力等级；允许手动调整提示强度与界面。查询本身无需先选年级、注册或填写孩子资料。

## 4. 六种产品方向

| 方向 | 核心承诺 | 差异化 | 成本与主要未知 |
|---|---|---|---|
| A. 极简笔顺查询器 | 随时查，几秒找到所需笔画 | 快、轻、准确、离线 | 最接近现有基础；使用频次和付费意愿待验证 |
| B. 小学生写字助手 | 看一遍、写一遍、复习易错处 | 作业中的短练习闭环 | 中等投入；要验证手写判定与纸上迁移效果 |
| C. 课内生字伴学 | 跟着当前课文预习与复习 | 教材字表和家庭工作流 | 内容维护较重；版次与内容授权需核实 |
| D. 教师课堂工具 | 更省时地演示和生成材料 | 投屏、字单、打印、分享 | 先轻工具后班级系统；需真实课堂反馈 |
| E. 汉字探索乐园 | 在游戏中理解笔画与部件 | 汉字结构、创意互动、文化内容 | 美术和内容投入较高；易偏离查询核心 |
| F. 智能书写教练 | 发现错误并给出具体练法 | 手写轨迹分析、个性化复习 | 研发验证成本高；不能由现有引擎直接推得 |

长期候选组合：**A 为入口，B 为主线，D 的投屏和打印作为低耦合扩展**。该组合在 Web 稳定后重新评估；C、E、F 可独立验证。

如果希望保持小而美，A + 生字本 + 打印即可成立；如果希望做持续学习产品，B + C 更值得研究；如果希望主要服务学校，D 应成为独立工作区。

## 5. 功能选择池：72 项

阶段符号：**首**＝未来所选产品方向的首版候选；**后**＝后续候选；**探**＝先验证价值或可行性。它们不代表当前 Web 重构的优先级或承诺。投入为相对复杂度，包含内容维护，不是工期估算。当前 Web 功能范围以独立计划为准。

### 5.1 查得到：输入与发现

| 编号 | 功能选项 | 用户价值与边界 | 阶段／投入 |

## 6. 内容与教学可信度

大陆简体版以教育部公开的《通用规范汉字笔顺规范》（GF 0023—2020）为核验依据。该规范给出《通用规范汉字表》8105 字的笔顺；这是规范范围，**不是本项目已覆盖或已审核字数**。教育部公开规范入口见文末来源。

建议为每个字管理以下内容：字符与规范版本、总笔画数、有序笔画、每笔名称、动画路径、拼音及适用语境、部首／教学部件、审核来源、审核日期、资源许可、冲突记录。

内容分三个状态：

- 已审核：关键教学内容有可追溯依据，通过数据一致性检查。
- 待审核：说明资源来源，避免使用“官方认证／完全准确”等表述。
- 有冲突：保留问题，安排校核；解决前不进入面向孩子的正式训练字包。

规范依据、动画路径许可、字典内容许可、教材内容许可是不同问题。上游引擎和数据有各自来源及许可，打印、打包和公开导出前分别核实，不根据引擎代码许可推断整个内容库可任意再分发。

内容供给按“已审核首发字包 → 首批目标教材字表 → 常用与易错字 → 更广字库”扩展。首发字包实际数量在盘点缺字、授权和审核工作量后确定，不能为了宣称全覆盖直接上线未经核验资源。

手写练习基于目标字进行轨迹和顺序匹配。HanziWriter 的 quiz、提示与回调可作为实现基础，但不会自然得到书法美观度、纸面笔顺或真实学习效果。掌握状态必须通过少提示独立完成及延迟复测来验证。

## 7. 平台路线选择

| 路线 | 适合条件 | 可复用内容 | 需验证的重点 |
|---|---|---|---|
| Web 优先 | 希望最快改善现有用户体验并测试需求 | 现有工程几乎全部 | 手机键盘、语音、缓存、后台恢复 |
| PWA | 希望可安装、轻量分发和离线字包 | Web 界面和核心 | 目标系统的安装流程、持久缓存与离线实际行为 |
| Web 核心＋原生容器 | 明确需要 iOS/Android 分发与部分系统入口 | 大部分界面、播放和数据逻辑 | 手写延迟、系统语音、生命周期、分享入口和资源包 |
| 跨平台原生界面 | App 长期以手写和系统体验为主 | 数据模型、资源与部分业务逻辑 | 现有 DOM/SVG 集成成本，具体渲染方案需原型验证 |
| 双端原生 | 复杂笔输入、深入系统能力成为核心优势 | 主要是内容和业务规则 | 维护成本与小团队承载能力 |
| 小程序 | 学校／家长分享传播是首要渠道 | 内容、规则可复用 | 渲染与交互适配、离线和平台能力需单独验证 |

确定顺序：**Web 先达到稳定验收，再建立 App 功能迁移清单，最后基于手机能力做增量设计并选择技术路线。** 上表是后续比较材料，不是与 Web 重构并行推进 App 的任务。详细阶段出口见 [Web 重构计划](Web重构计划.md)。

## 8. 研究、经营与待决策事项

建议先做小规模方向验证：访谈 5—8 个家庭和 2—3 位教师，覆盖低年级、高年级与不同输入设备；该样本用于发现交互问题，不用于估计市场规模。任务包括“查不知道读音的字”“确认第 N 笔”“纸上跟写”“从一组作业字中切换”。比较极简查询版与查询＋练习版，观察完成过程和阻碍。

商业模式可保留四种选择：公益／免费工具；基础查询免费、付费离线与打印等增强包；包含持续内容服务的家庭订阅；面向教师的材料与课堂工具包。暂不定价，先验证使用频率、持续价值和内容维护成本。建议核心学习页保持无广告、无社交排名；购买和资料管理放在家长可理解的独立入口。

默认本地使用，不强制实名或账号。查询记录、手写轨迹、照片和语音分别定义用途与保存期限；摄像头和麦克风只在用户触发相应功能时申请。若后续接云端识别，清楚展示上传内容与删除方式；不把儿童输入默认用于模型训练。现有页面带有第三方统计脚本，面向儿童的版本应先重新审视统计需求与最小数据方案，避免直接继承。

后续需要选择而不阻塞本轮探索的五个问题：

1. 主方向：轻查询、家庭练习、教材伴学、教师工具，谁是第一优先？
2. 首批设备：手机、iPad／安卓平板，还是课堂电脑？
3. 内容范围：大陆简体优先是否适合；先做哪些字包？
4. 手写目标：屏幕练习为主，还是纸上练字辅助为主？
5. 产品目标：小而美长期工具，还是持续内容与教学服务？

建议默认答案：小学低年级家庭、手机查询＋平板练习、大陆简体审核字包、纸屏结合、轻量学习助手。它是便于下一轮细化的起点，不代表已替用户锁定方案。
